# TDD Refactor

## 목적

현재 테스트 통과 상태를 유지하면서 코드 구조를 개선한다. `$ARGUMENTS`는 반드시 `<카테고리>-<이슈번호>` 형식의 이슈 식별자여야 한다. 예를 들어 `tag-1`은 `tag` 카테고리의 1번 이슈를 의미하는 단순 예시다.

## 입력 규칙

- 실행 인자는 반드시 `<카테고리>-<이슈번호>` 형식으로 전부 전달되어야 한다.
- 예: `tag-1`, `note-3`, `search-12`.
- 인자가 없거나 단순 숫자만 전달되면 어떤 카테고리의 이슈인지 알 수 없으므로 스킬을 실행하지 않는다.
- 잘못된 입력이면 리팩토링을 시작하지 말고 `<카테고리>-<이슈번호>` 형식으로 다시 요청해 달라고 안내한다.

## 절대 제약

- 새 기능을 추가하지 않는다.
- 의도적으로 동작을 변경하지 않는다.
- 테스트 파일을 수정하지 않는다.
- `src/` 디렉토리 밖 파일을 수정하지 않는다.
- `git diff main...HEAD --name-only -- src/` 결과 밖 파일을 수정하지 않는다.
- 한 번에 하나의 작고 동작 보존적인 리팩토링만 수행한다.
- 리팩토링 후 테스트가 깨지면 해당 리팩토링만 즉시 롤백한다.

## 실행 순서

1. `$ARGUMENTS`가 `<카테고리>-<이슈번호>` 형식으로 완전히 전달되었는지 확인한다. 형식이 맞지 않으면 즉시 중단하고 인자를 작성해 달라고 요청한다.
2. `AGENTS.md`를 먼저 읽고 프로젝트별 네이밍, 아키텍처, 스타일, 테스트, Git 규칙을 파악한다.
3. 수정 전에 `npm test`를 실행해 전체 테스트 통과 상태를 확인한다.
   - baseline 테스트가 실패하면 리팩토링하지 말고 실패 내용을 보고한다.
4. 리팩토링 대상 후보 파일을 식별한다.
   - `git diff main...HEAD --name-only -- src/`를 실행한다.
   - `*.test.ts`, `*.test.tsx` 파일은 제외한다.
   - 생성 파일이나 소스가 아닌 파일이 포함되면 제외한다.
5. 남은 파일만 아래 기준으로 검토한다.
   - 중복 제거: 같은 로직이나 변환이 반복되는가.
   - 네이밍 명확성: 이름이 의도와 책임을 드러내는가.
   - 단일 책임: 함수나 컴포넌트가 너무 많은 일을 하는가.
   - 불필요한 복잡도: 매직 넘버, 과도한 중첩, 불필요한 추상화, 죽은 분기가 있는가.
   - 프로젝트 컨벤션 불일치: `AGENTS.md`와 주변 코드 패턴에 어긋나는가. 저장소에 `CLAUDE.md`가 있으면 함께 확인한다.
6. 리팩토링 후보 목록을 개발자에게 보고하고 명시적 승인을 기다린다.
7. 승인 후 후보를 하나씩 처리한다.
   - 승인된 대상 파일만 수정한다.
   - 수정 직후 `npm test`를 실행한다.
   - 테스트가 통과한 경우에만 다음 후보로 이동한다.
8. `npm test`가 실패하면 다음 순서로 처리한다.
   - 가장 최근 리팩토링만 롤백한다.
   - `npm test`를 다시 실행해 통과 상태 복구를 확인한다.
   - 더 작은 접근으로 재시도하거나 안전하지 않은 이유를 보고한다.
9. 완료 시 리팩토링 전후 요약을 제공한다.
   - 입력 이슈 식별자.
   - baseline 테스트 결과.
   - 수행한 리팩토링 목록.
   - 각 단계 후 실행한 테스트 결과.
   - 검토했지만 건너뛴 후보와 이유.

## 승인 요청 형식

수정 전에는 다음처럼 간결하게 보고한다.

```text
이슈: <카테고리>-<이슈번호>
Baseline: npm test 통과
리팩토링 후보:
- src/path/File.tsx: <구체적인 리팩토링 이유>
- src/path/util.ts: <구체적인 리팩토링 이유>

승인 전에는 파일을 수정하지 않겠습니다.
```

안전한 후보가 없으면 후보가 없다고 보고하고 수정 없이 종료한다.
