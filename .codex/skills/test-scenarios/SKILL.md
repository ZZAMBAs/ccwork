# Test Scenarios

## 목적

이슈 단위로 `시그니처 확정 -> 테스트 시나리오 도출`을 순서대로 처리한다. 이후 TDD로 테스트 코드를 작성하기 전 단계만 담당하며, 구현 코드와 테스트 코드는 작성하지 않는다.

## 사용법

사용자가 다음처럼 이슈 번호를 함께 입력하면 이 스킬을 사용한다.

```text
/test-scenarios 카테고리-이슈번호
```

이슈 번호가 없으면 절대 기본값을 추정하지 않는다. 특히 `1`번 이슈로 간주하지 않는다. 이 경우 다음 취지로만 짧게 답하고 즉시 종료한다.

```text
카테고리와 이슈 번호를 함께 적어 주세요. 예: /test-scenarios tag-1
```

## 참고 대상

- GitHub Issue: 사용 가능한 GitHub MCP 도구가 있으면 우선 고려한다. MCP가 없거나 필요한 조회를 할 수 없으면 github CLI 도구를 사용한다.
- GitHub Issue 조회가 MCP와 `gh` CLI 모두에서 실패하면 로컬 이슈 문서를 대체 근거로 사용하고, 어떤 조회 수단이 실패했는지 개발자에게 명확히 알린다.
- PRD: 이슈와 관련된 `docs/features/{category}/prd.md`를 우선 사용한다. 파일이 없으면 현재 저장소에 존재하는 `docs/feature/{category}/prd.md` 같은 PRD 경로를 사용한다.
- 로컬 이슈 문서: `docs/features/{category}/issue-{N}.md`를 우선 사용한다. 파일이 없으면 현재 저장소에 존재하는 `docs/feature/{category}/issue/{NN}-*.md` 같은 번호 매칭 문서를 사용한다.
- github 이슈 문서: github 내 이슈 번호와 관계 없이 로컬 이슈 문서와 관련된 문서를 찾는다. 보통은 `[{카테고리}-{이슈번호}]` 형태로 시작한다.
- 코드베이스: 시그니처 확정 전에 관련 파일을 반드시 읽는다. 특히 `src/api/notes.ts`, `src/context/NotesContext.tsx`, `src/components/`, `src/types/`의 기존 패턴을 확인한다.

## 실행 순서

### 1. 시그니처 확정안 작성

GitHub Issue, PRD, 이슈 문서, 코드베이스를 근거로 구현 전 시그니처만 제안한다. 구현 코드는 절대 작성하지 않는다.

GitHub Issue 본문과 AC는 GitHub MCP 또는 `gh issue view $ARGUMENTS` 중 현재 환경에서 사용 가능한 방법으로 확인한다. 둘 다 사용할 수 없을 때만 로컬 이슈 문서를 대체 근거로 사용한다.

포함할 항목:

- 함수 시그니처: 이름, 파라미터 타입, 반환 타입
- 에러 케이스: 어떤 상황에서 에러를 던지거나 오류 상태를 반환하는지
- 컴포넌트 Props 타입 정의
- 필요한 공용 도메인 타입 변경
- `src/api/notes.ts`, `NotesContext`, 컴포넌트 Props, `src/types` 기존 패턴과의 정합성

이름과 경계는 기존 코드베이스를 따른다. API 함수와 Context 액션은 기존 동사 네이밍과 상태 소유권을 우선한다.

### 2. 시그니처 검토 및 승인 요청

확정안을 개발자에게 보여주고 승인 여부를 묻는다. 개발자가 승인하거나 수정 지시를 하기 전까지 다음 단계로 넘어가지 않는다.

승인 전에는 파일에 시그니처를 기록하지 않는다.

### 3. 승인된 시그니처 기록

승인 후 이슈 문서 상단에 승인된 시그니처를 기록한다.

사용할 제목:

```markdown
## 확정 시그니처
```

기존 문서는 보존한다. 관련 없는 문구, 인코딩, 형식은 임의로 고치지 않는다.

### 4. 테스트 시나리오 도출

승인된 시그니처를 기준으로 테스트 시나리오를 도출한다. 테스트 코드는 작성하지 않는다.

시나리오는 다음 셋 중 하나로 분류한다.

- 정상
- 경계
- 예외

각 시나리오는 다음 형식을 반드시 따른다.

```text
[정상/경계/예외] 함수명 — should [기대동작] when [조건]
```

컴포넌트 동작은 `NoteEditor.addTag`처럼 테스트할 수 있는 안정적인 동작 이름을 사용한다.

### 5. 테스트 시나리오 기록

이슈 문서 하단에 테스트 시나리오를 추가한다.

사용할 제목:

```markdown
## 테스트 시나리오
```

이미 같은 섹션이 있으면 중복 생성하지 않고 기존 섹션을 갱신한다.

### 6. Acceptance Criteria 커버리지 대조

GitHub Issue의 AC 목록은 GitHub MCP 또는 `gh issue view $ARGUMENTS` 중 현재 환경에서 사용 가능한 방법으로 다시 확인한다.

- 각 AC 항목이 최소 1개 이상의 시나리오로 커버되는지 확인한다.
- 커버되지 않은 AC가 있으면 시나리오를 추가한다.
- 최종 응답에 AC 커버리지 요약을 포함한다.

GitHub MCP와 `gh issue view`가 모두 인증, 네트워크, 저장소 메타데이터, CLI 미설치 문제로 실패하면 로컬 이슈 문서를 대체 근거로 사용하고 그 제한을 명확히 알린다.

### 7. 시나리오 검토 및 승인 요청

최종 시나리오 목록과 AC 커버리지 요약을 개발자에게 보여주고 승인 여부를 묻는다. 승인 전까지 구현이나 테스트 코드 작성 단계로 넘어가지 않는다.

## 금지 사항

- 구현 코드를 작성하지 않는다.
- 테스트 코드를 작성하지 않는다.
- 동작, 스타일, 프로덕션 파일을 변경하지 않는다.
- 선택한 이슈 밖으로 범위를 넓히지 않는다.
- 승인 게이트를 건너뛰지 않는다.
- 기존 저장소의 네이밍과 파일 구조를 임의로 바꾸지 않는다.
