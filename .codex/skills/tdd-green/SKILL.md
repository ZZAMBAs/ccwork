# TDD Green

## 목적

현재 실패 중인 테스트를 통과시키는 최소한의 구현 코드만 작성한다. 이 스킬은 TDD의 green 단계만 담당하며, 테스트에 없는 기능을 미리 구현하지 않는다.

## 사용법

사용자가 `카테고리-이슈번호`를 함께 입력하면 이 스킬을 사용한다.

```text
/tdd-green <category-issueNumber>
```

입력 형식은 `{category}-{issueNumber}`로 해석한다.

- `category`: 기능 문서 폴더명. 예: `tag`
- `issueNumber`: 기능 안의 이슈 번호. 예: `1`

입력이 없거나 형식이 맞지 않으면 어떤 기능도 처리하지 않는다. 값을 추정하지 말고 아래 문장만 안내한 뒤 즉시 종료한다.

```text
카테고리-이슈번호 입력값이 필요합니다. 예: /tdd-green <category-issueNumber>
```

## 참고 대상

입력값이 `{category}-{issueNumber}`이면 다음 순서로 이슈 문서를 찾는다.

1. `docs/feature/{category}/issue/{NN}-*.md`
2. `docs/feature/{category}/issue-{issueNumber}.md`
3. `docs/features/{category}/issue/{NN}-*.md`
4. `docs/features/{category}/issue-{issueNumber}.md`

이슈 번호의 파일명 검색에는 두 자리 0 패딩을 허용한다. 예: `1` -> `01-*.md`.

디자인과 스타일링 확인 대상:

- `docs/design/design.md`
- 구현 대상 UI와 연결된 `docs/design/` 하위 상세 문서
- 이슈 문서의 `디자인 참고` 섹션
- `AGENTS.md`의 스타일링, 구현, 테스트 규칙

문서나 섹션이 없으면 해당 항목만 건너뛰고, 남아 있는 프로젝트 컨벤션을 따른다.

## 실행 순서

### 1. 실패 테스트 확인

먼저 전체 테스트를 실행한다.

```bash
npm test
```

실패한 테스트 파일, 테스트 이름, 에러 메시지를 확인한다. 수집 실패나 import 실패가 있으면 그 문제를 먼저 처리한다.

### 2. collect 실패 감지

이슈 문서의 미완료 시나리오 체크박스와 Vitest가 보고하는 테스트 수를 비교한다.

- 이슈 문서에서 `- [ ]` 체크박스 수를 센다. 만약 이러한 체크박스가 없다면 그 이슈 문서 내 테스트 시나리오마다 체크 박스를 생성한다.
- Vitest 출력의 `Tests` 수와 비교한다.
- 수가 맞지 않고 import 대상 모듈이 없어서 테스트가 수집되지 않는 상황이면, 확정 시그니처만 가진 stub 구현 파일을 만든다.
- stub 단계에서는 import와 타입 검사를 통과하는 데 필요한 코드만 작성한다.

### 3. 디자인 컨텍스트 로드

UI 컴포넌트를 수정하기 전에는 참고 대상의 디자인 문서를 읽는다.

- 테스트가 요구하는 동작을 충족하면서 문서에 명시된 Tailwind 클래스, 레이아웃, 색상, 간격, 상태 표현을 적용한다.
- 디자인 문서에 없는 시각적 요소를 임의로 추가하지 않는다.
- 디자인 문서와 사용자 요청이 충돌하면 범위를 넓혀 고치지 말고 사용자에게 확인한다.

### 4. 첫 번째 실패 테스트 통과

첫 번째 실패 테스트를 통과시키는 최소 구현만 작성한다.

- 구현 파일은 생성 또는 수정할 수 있다.
- 테스트 파일은 절대 수정하지 않는다.
- 기존 컴포넌트, Context, API, 타입 경계를 우선 따른다.
- 테스트가 요구하지 않는 예외 처리, UI 상태, 확장 동작은 만들지 않는다.
- 불필요한 추상화나 공용 유틸은 만들지 않는다.

### 5. 테스트 실행과 피드백 루프

다시 전체 테스트를 실행한다.

```bash
npm test
```

해당 테스트가 아직 실패 중이면 에러 메시지를 읽고 원인을 분석해 코드를 수정한 뒤 다시 실행한다. 같은 테스트에 대해 최대 4회 반복한다.

4회 후에도 실패하면 중단하고 다음 내용을 보고한다.

- 계속 실패하는 테스트
- 마지막 에러 메시지
- 추정 원인
- 현재까지 수정한 파일

### 6. 시나리오 체크

테스트가 통과하면 이슈 문서에서 대응되는 항목만 `- [ ]`에서 `- [x]`로 변경한다.

관련 없는 항목은 체크하지 않는다.

### 7. 다음 실패 테스트 처리

다음 실패 테스트로 이동해 4번부터 반복한다. 전체 테스트가 통과하거나 명확한 blocker가 생길 때까지 진행한다.

### 8. 커버리지 측정

전체 테스트가 통과한 뒤 커버리지를 측정한다.

```bash
npx vitest run --coverage
```

미커버 라인을 확인하고 시나리오에서 빠진 케이스인지 보고한다. 커버리지를 올리기 위한 테스트 추가는 하지 않는다.

## 제약

- 테스트 파일은 수정하지 않는다.
- 테스트에 없는 기능은 구현하지 않는다.
- 사용자 입력 검증이나 저장 실패 처리에 `alert`를 사용하지 않는다.
- 문구나 인코딩 수정이 목표가 아니면 기존 문자열을 정리하지 않는다.
- 스타일/UI 변경은 `docs/design/design.md`와 연결된 상세 문서 범위 안에서만 수행한다.
- 필요한 의존성이 이미 없다면 임의로 설치하지 말고 사용자에게 확인한다.

## 완료 보고

완료 시 다음을 요약한다.

- 생성 또는 수정한 구현 파일
- 체크한 이슈 문서 항목
- 최종 `npm test` 결과
- `npx vitest run --coverage` 결과와 미커버 라인 판단
- 남은 blocker나 위험
