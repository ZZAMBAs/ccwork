# Feature Planner

## 개요

하나의 기능을 초기 아이디어에서 개발 가능한 작업 단위로 변환한다.

```text
spec-original.md
  -> spec-fixed.md
  -> prd.md
  -> issues.md + GitHub Issues
```

모든 산출물은 `docs/features/{name}/` 아래에 둔다. 기획 전에는 관련 코드를 읽고, 현재 프로젝트의 아키텍처, 네이밍, 테스트, UI 규칙을 제약 조건으로 사용한다.

## 전체 절차

1. `docs/features/{name}/spec-original.md`에서 시작한다. 사용자가 아이디어만 제공하면 이 파일부터 만든다.
2. 요구사항 인터뷰를 진행하고 `spec-fixed.md`를 작성한다.
3. 사용자가 `spec-fixed.md`를 확정할 때까지 `[GATE]`에서 멈춘다.
4. `prd.md` 초안을 만들고 아키텍처 3안을 비교한 뒤, 사용자가 하나를 선택할 때까지 `[GATE]`에서 멈춘다.
5. 선택된 안을 ADR 형식으로 작성하고 Out of Scope을 완성한 뒤, 사용자가 범위를 확정할 때까지 `[GATE]`에서 멈춘다.
6. PRD를 수직 슬라이스 이슈로 분해해 `issues.md`를 작성하고, 사용자가 이슈 목록을 확정할 때까지 `[GATE]`에서 멈춘다.
7. GitHub Issue 생성과 프로젝트 보드 등록은 사용자가 명시적으로 승인하고 필요한 `gh` 정보가 준비된 뒤에만 진행한다.

게이트를 건너뛰지 않는다. 사용자가 명시적으로 구현 전환을 요청하지 않는 한 기능 구현을 시작하지 않는다.

## 단계 1: 요구사항 인터뷰

### 목적

초기 기능 정의의 모호성을 제거하고, 구현 전에 엣지 케이스와 결정 사항을 확정한다.

### 입력

- `docs/features/{name}/spec-original.md`
- 기존 코드베이스 구조와 패턴

### 수행

Codex를 인터뷰어로 사용한다. 한 번에 하나씩 질문하고, 추천 답변과 그 이유를 함께 제시한다. 다음 영역을 반드시 다룬다.

1. 이 기능의 primary user.
2. 최소 동작 시나리오 3개.
3. 데이터 저장 방식과 기존 구조와의 관계.
4. 최대값, 빈 값, 중복, 동시성 같은 경계 조건.
5. 실패 시 사용자에게 표시할 오류 처리 방식.
6. 기존 UI 패턴과 재사용 가능한 컴포넌트.
7. 응답 시간, 데이터 크기 같은 성능 제약.
8. 향후 확장 가능성과 다음 기능에 미치는 영향.

인터뷰 중에는 유비쿼터스 언어를 확정한다.

- 코드, 문서, 대화에서 같은 단어로 같은 대상을 가리키게 한다.
- `spec-fixed.md`에 `용어 정의` 섹션을 추가한다.

### 산출물

- `docs/features/{name}/spec-fixed.md`

### 승인 게이트

```text
[GATE] 사용자가 spec-fixed.md를 읽고 확정할 때까지 대기
```

## 단계 2: PRD 작성과 ADR

### 목적

요구사항, 디자인, 기술 결정, 범위를 하나의 기준 문서로 통합한다.

### 입력

- `docs/features/{name}/spec-fixed.md`
- `docs/features/{name}/design.md`가 있으면 함께 참조
- 기존 코드베이스 패턴

### PRD 구조

`docs/features/{name}/prd.md`는 다음 구조로 작성한다.

- `개요`: 기능의 목적과 범위.
- `사용자 스토리`: 사용자 관점의 흐름.
- `기술 결정`: ADR 형식의 결정.
- `Out of Scope`: 이번 범위에서 제외할 항목.
- `용어 정의`: `spec-fixed.md`의 용어와 동기화.

### 아키텍처 3안 비교

최종 기술 결정을 작성하기 전에 최소 3가지 안을 제안하고, 아래 7가지 고정 기준으로 비교한다.

| #   | 기준                 | 비교 내용                                         |
| --- | -------------------- | ------------------------------------------------- |
| 1   | 데이터 구조          | 데이터를 어떤 형태로 저장하고 표현하는가          |
| 2   | API 레이어 변경지점  | 기존 API 레이어에서 무엇이 바뀌는가               |
| 3   | 상태관리 변경지점    | Context 또는 Store에서 무엇이 추가되거나 바뀌는가 |
| 4   | 핵심 동작            | 가장 중요한 동작을 어떻게 구현하는가              |
| 5   | 컴포넌트 구조        | 어떤 컴포넌트가 추가되거나 수정되는가             |
| 6   | 기존 패턴과의 일관성 | 현재 코드베이스 관습과 얼마나 맞는가              |
| 7   | 테스트 용이성        | 단위 테스트나 E2E 테스트가 얼마나 쉬운가          |

비교 뒤에는 멈춘다.

```text
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기
```

### ADR 작성 형식

사용자가 안을 선택하면 PRD의 기술 결정 섹션에 다음 4요소로 작성한다.

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.
**Decision** — 무엇을 선택했는가.
**Alternatives** — 거부한 안과 각각의 거부 이유. 이유 없는 거부 금지.
**Consequences** — 트레이드오프. 장점뿐 아니라 단점도 반드시 명시한다.
```

### Out of Scope

하지 않을 것을 구체적으로 나열한다. 명시하지 않은 범위까지 구현이 확장되지 않도록 경계를 분명히 한다.

```text
[GATE] 사용자가 Out of Scope을 읽고 확정할 때까지 대기
```

### 산출물

- `docs/features/{name}/prd.md`

## 단계 3: 이슈 분해

### 목적

PRD를 실행 가능한 작업 단위로 변환한다. 각 이슈는 독립적으로 TDD 사이클을 돌릴 수 있어야 한다.

### 입력

- `docs/features/{name}/prd.md`
- GitHub 등록을 요청받은 경우 프로젝트 보드 정보

### 수직 슬라이싱

각 이슈마다 다음 질문을 적용한다.

```text
이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?
```

- Yes이면 수직 슬라이스로 유지한다.
- No이면 다른 이슈와 합치거나 다시 나눈다.

API -> Context -> UI처럼 레이어별로 수평 분리하지 않는다. 앞 이슈의 결과가 다음 이슈의 입력이 되도록 의존성 순서를 잡고, 역방향 개발을 피한다.

### 이슈 크기

반나절에서 하루 안에 Red-Green-Refactor 사이클을 완료할 수 있는 크기를 목표로 한다. 피드백이 느릴 만큼 크면 나누고, 사용자에게 보이는 동작 없이 PR 오버헤드만 늘어날 만큼 작으면 합친다.

### Acceptance Criteria

모든 이슈에는 구체적인 Given-When-Then 기준을 포함한다.

```markdown
## Acceptance Criteria

- [ ] Given [사전 조건], When [행동], Then [기대 결과]
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
```

Acceptance Criteria는 이후 테스트 시나리오의 기반이 된다.

### 산출물

- `docs/features/{name}/issues.md`
- 사용자가 승인한 경우 AC가 포함된 GitHub Issues
- 사용자가 승인한 경우 프로젝트 보드 Todo 항목

### 승인 게이트

```text
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스 기준 충족을 확인할 때까지 대기
```

## GitHub 등록

사용자가 승인하고 대상 owner, repository, project number, 인증 상태를 확인한 뒤에만 GitHub 명령을 실행한다.

```bash
gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"
gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>
```

## 게이트 요약

| 지점                    | 확인 내용                                            |
| ----------------------- | ---------------------------------------------------- |
| 단계 1 후               | `spec-fixed.md`: 모호성 제거, 용어 확정              |
| 단계 2 아키텍처 비교 후 | 사용자가 3안 중 하나를 선택                          |
| 단계 2 범위 확정 후     | Out of Scope이 구체적이고 승인됨                     |
| 단계 3 후               | 이슈가 수직 슬라이스이고 AC와 의존성 순서가 구체적임 |
