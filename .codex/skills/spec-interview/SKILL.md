# Spec Interview

## 개요

기능 아이디어를 구현 가능한 상세 요구사항으로 구체화한다. 이 스킬은 질문을 통해 모호성을 제거한 뒤 `docs/feature/{name}/spec-fixed.md`를 산출한다.

## 시작 절차

1. 사용자의 기능 요청에서 feature name을 추정한다.
2. feature name은 `docs/feature/{name}/` 경로에 맞는 짧은 kebab-case로 정한다.
3. `docs/feature/{name}/spec-original.md`가 있으면 먼저 읽는다.
4. `docs/feature/{name}/spec-fixed.md`가 이미 있으면 기존 확정 사항을 이어받아 읽는다.
5. 관련 코드가 있으면 구현 전에 반드시 읽는다. README나 사용자 설명만으로 판단하지 않는다.
6. 문서가 없고 사용자가 아이디어만 말했으면, 그 아이디어를 기준으로 인터뷰를 시작한다.

경로가 애매하면 저장소 기존 기능 문서 관례를 우선한다. 이 프로젝트에서는 `docs/feature/{name}/`를 사용한다.

## 인터뷰 방식

한 번에 하나의 질문만 한다. 질문에는 가능하면 추천 답변과 추천 이유를 포함한다.

질문 형식:

```text
질문 N: [확인할 내용]

추천안: [구체적인 추천 답변]

이유: [추천하는 이유와 코드베이스/요구사항상 장점]
```

사용자가 "추천대로", "좋아", "그렇게 하자", "네가 정해"처럼 답하면 추천안을 확정한다. 사용자가 이후 질문도 임의로 추천대로 진행하라고 하면, 남은 결정은 보수적인 추천안으로 확정하고 `spec-fixed.md`를 작성한다.

## 질문 범위

아래 영역을 최대한 빠짐없이 다룬다. 이미 문서나 코드에서 확정된 내용은 다시 묻지 말고 `spec-fixed.md`에 반영한다.

1. Primary user: 누가 이 기능을 쓰는가.
2. 최소 동작 시나리오: 가장 기본적인 사용 흐름 3개 이상.
3. 데이터 구조: 기존 타입, API, 저장 구조와의 관계.
4. 상태 소유권: 로컬 상태, Context, URL, 서버 상태 중 어디에 둘 것인가.
5. 경계 조건: 빈 값, 최대값, 중복, 삭제, 동시성, 선택 상태, 권한 같은 조건.
6. 에러 처리: 실패를 사용자에게 어떻게 보여주고, 어디에 기록할 것인가.
7. UI와 상호작용: 기존 컴포넌트와 디자인 패턴을 어떻게 재사용할 것인가.
8. 성능 제약: 데이터 크기, 응답 시간, debounce, memoization, 서버 처리 필요성.
9. 접근성: 키보드 조작, focus, 버튼 요소, 레이블, 스크린리더 고려.
10. 테스트 관점: 수용 기준과 나중에 테스트 시나리오로 바꿀 수 있는 조건.
11. 향후 확장성: 이번 결정이 다음 기능에 미치는 영향.

## 코드베이스 참고

기능과 관련된 파일을 먼저 읽고 질문의 추천안을 만든다.

- 데이터 타입은 `src/types`를 확인한다.
- API 호출은 `src/api`를 확인한다.
- 서버 상태와 CRUD 흐름은 Context 또는 store를 확인한다.
- UI 작업이면 관련 컴포넌트와 `docs/design/design.md`를 확인한다.
- 기존 기능 문서가 있으면 `docs/feature/*`의 형식과 용어를 참고한다.

코드베이스에서 확인한 사실과 추론을 구분한다. 불확실한 내용은 질문으로 남긴다.

## spec-fixed.md 작성 규칙

인터뷰가 충분히 진행되거나 사용자가 남은 질문을 모두 추천대로 진행하라고 하면, 바로 파일을 쓰지 말고 먼저 전체 요구사항 요약을 제시한다. 사용자가 요약을 확정한 뒤 `docs/feature/{name}/spec-fixed.md`를 작성하거나 갱신한다.

요약에는 다음을 포함한다.

- 만들 기능의 목적
- primary user
- 최소 동작 시나리오
- 확정된 데이터와 상태 관리 방향
- 주요 경계 조건
- 오류 처리 방향
- UI와 상호작용 방향
- 성능과 접근성 고려사항
- 고정할 용어

요약 뒤에는 다음처럼 확인한다.

```text
위 요구사항 요약으로 spec-fixed.md를 작성해도 될까요?
```

필수 섹션:

- 문서 목적
- 핵심 방향
- Primary User
- 최소 동작 시나리오
- 기능 요구사항
- 데이터와 상태 관리
- UI 동작
- 경계 조건
- 에러 처리
- 성능 제약
- 접근성과 상호작용
- 용어 정의
- 확인된 결정 사항

기능 성격에 맞지 않는 섹션은 짧게 쓰되 생략하지 않는다. 이후 구현자가 같은 요구사항을 재구성하지 않아도 될 만큼 구체적으로 작성한다.

## 용어 정의

`spec-fixed.md`에는 반드시 `용어 정의` 섹션을 둔다.

- 기능 안에서 반복되는 핵심 명사를 고정한다.
- 코드, 문서, 대화에서 같은 단어가 같은 개념을 가리키게 한다.
- 이후 같은 기능 구현이나 인접 기능 구현에서도 재사용할 수 있게 쓴다.

## 완료

사용자가 요구사항 요약을 확정하면 `spec-fixed.md`를 작성한다. 작성 후에는 파일 경로와 반영한 핵심 결정 사항만 간단히 알린다.
