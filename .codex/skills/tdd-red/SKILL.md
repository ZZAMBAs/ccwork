# TDD Red

## 목적

승인된 테스트 시나리오를 실패하는 테스트 코드로 작성한다. 이 스킬은 TDD의 red 단계만 담당하며, 구현 코드나 production 코드는 작성하지 않는다.

## 사용법

사용자가 `카테고리-이슈번호`를 함께 입력하면 이 스킬을 사용한다.

```text
/tdd-red <category-issueNumber>
```

입력 형식은 `{category}-{issueNumber}`로 해석한다.

- `category`: 기능 문서 폴더명. 예: `tag`
- `issueNumber`: 기능 안의 이슈 번호. 예: `1`

입력이 없거나 형식이 맞지 않으면 어떤 기능도 처리하지 않는다. 값을 추정하지 말고 아래 문장만 안내한 뒤 즉시 종료한다.

```text
카테고리-이슈번호 입력 값이 필요합니다. 예: /tdd-red <category-issueNumber>
```

## 참고 대상

입력값이 `{category}-{issueNumber}`이면 다음 순서로 문서를 찾는다.

1. `docs/features/{category}/issue-{issueNumber}.md`
2. `docs/feature/{category}/issue-{issueNumber}.md`
3. `docs/features/{category}/issue/{NN}-*.md`
4. `docs/feature/{category}/issue/{NN}-*.md`

이슈 번호는 파일명 검색 시 두 자리 0 패딩도 허용한다. 예: `1` -> `01-*.md`.

문서에서 반드시 읽을 섹션:

- `## 확정 시그니처`
- `## 테스트 시나리오`

코드 패턴 확인 대상:

- 기존 테스트 파일
- `vite.config.ts`
- `src/test-setup.ts`
- 테스트 대상 파일의 import/export 형태

## 실행 순서

### 1. 시나리오와 시그니처 읽기

기능 이슈 문서에서 확정 시그니처와 승인된 테스트 시나리오를 읽는다.

- `## 확정 시그니처`가 없으면 중단하고 시그니처 확정이 먼저 필요하다고 알린다.
- `## 테스트 시나리오`가 없으면 중단하고 테스트 시나리오 승인이 먼저 필요하다고 알린다.
- 시나리오가 승인되었는지 대화 맥락이나 문서 상태로 확인할 수 없으면 개발자에게 확인한다.

### 2. 테스트 대상과 파일 결정

각 시나리오를 함수 또는 컴포넌트 단위 테스트 파일에 배치한다.

테스트 파일 컨벤션:

- 테스트 대상 파일과 같은 디렉토리에 둔다.
- 파일명은 `{파일명}.test.ts` 또는 `{파일명}.test.tsx`를 사용한다.
- 예:
  - `src/api/tags.ts` -> `src/api/tags.test.ts`
  - `src/utils/tags.ts` -> `src/utils/tags.test.ts`
  - `src/components/TagInput.tsx` -> `src/components/TagInput.test.tsx`
- `describe` 블록은 함수 또는 컴포넌트 단위로 묶는다.
  - 예: `describe('addTagsToList', () => { ... })`
  - 예: `describe('TagInput', () => { ... })`

테스트 대상 구현 파일이 아직 없더라도 red 단계에서는 예상 경로의 테스트 파일을 만든다. 이 경우 import 실패도 red 실패로 허용한다.

### 3. 시나리오별 테스트 작성과 즉시 실행

시나리오를 하나씩 테스트 코드로 작성한다.

- 테스트 이름은 반드시 `should [기대 동작] when [조건]` 형식을 사용한다.
- 시나리오 앞의 `[정상]`, `[경계]`, `[예외]` 분류는 테스트 이름에 넣지 않는다.
- Vitest를 사용한다.
- React 컴포넌트 테스트에는 React Testing Library를 사용한다.
- 사용자 상호작용에는 가능한 경우 `@testing-library/user-event`를 사용한다.
- `@testing-library/user-event`가 프로젝트에 없으면 설치하지 말고 기존 의존성으로 가능한 `fireEvent`를 사용한다.

각 시나리오 작성 직후 가장 좁은 테스트 명령을 실행한다.

- 단일 테스트 파일 또는 테스트명 필터를 우선한다.
- 방금 작성한 테스트가 실패하는지 확인한 뒤 다음 시나리오로 이동한다.
- 실패 원인이 테스트 문법 오류, 잘못된 import 경로, 테스트 자체의 불가능한 전제라면 테스트를 수정한다.
- 실패 원인이 구현 누락 또는 기능 미구현이면 정상적인 red 실패로 본다.

### 4. 전체 red 확인

모든 시나리오를 테스트로 작성한 뒤 `npm test`를 실행한다.

- 새로 작성한 테스트들이 실패해야 한다.
- 기존 테스트가 있다면 기존 테스트 실패와 신규 red 실패를 구분해 보고한다.
- 신규 테스트가 통과하면 red 단계가 아니므로 테스트가 실제 요구 동작을 검증하는지 재검토한다.

## 제약

- 테스트 파일만 생성하거나 수정한다.
- `src`의 구현 파일은 절대 수정하지 않는다.
- 타입, API, 컴포넌트, 유틸 구현을 만들지 않는다.
- 테스트 통과를 위해 production 코드를 변경하지 않는다.
- 패키지를 설치하지 않는다.
- 스냅샷 파일을 새로 만들지 않는다.
- 테스트 시나리오 범위를 임의로 넓히지 않는다.

## 완료 보고

완료 시 다음을 요약한다.

- 생성 또는 수정한 테스트 파일
- 작성한 테스트 수
- 시나리오별 red 실패 확인 결과
- 최종 `npm test` 결과
- 구현 단계에서 해결해야 할 대표 실패 원인
