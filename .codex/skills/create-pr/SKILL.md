# Create PR

현재 브랜치의 변경사항을 검토해 PR 초안을 만들고, 개발자 승인과 E2E 검증을 거친 뒤 PR을 생성한다.

## 원칙

- PR 생성 전에는 반드시 현재 브랜치, base 브랜치, 변경 범위, 테스트 상태를 확인한다.
- 사용자의 기존 변경사항을 되돌리지 않는다.
- 초안 승인 전에는 `npm run test:e2e`, `git push`, `gh pr create`, MCP PR 생성 작업을 실행하지 않는다.
- E2E 실패 시 PR 생성을 중단한다. E2E 테스트 코드를 고쳐 통과시키지 않는다.
- 커밋이 필요한 상태라면 임의로 커밋하지 말고 사용자에게 커밋 범위와 메시지 승인을 요청한다.

## 절차

1. 현재 상태를 파악한다.
   - `git status --short --branch`
   - `git branch --show-current`
   - `git remote -v`
   - `git diff --stat`
   - 필요 시 `git diff`, `git log --oneline --decorate -n 10`, `git merge-base` 기반 diff를 확인한다.
   - 가능하면 base 브랜치는 `main`을 기본값으로 삼되, 원격 추적 브랜치나 현재 작업 맥락에서 더 적절한 base가 보이면 명시한다.

2. PR 초안을 작성한다.
   - 제목은 간결한 한국어 커밋/PR 스타일로 작성한다.
   - 본문은 다음 구조를 기본으로 한다.

```markdown
## 변경 사항

- ...

## 검증

- [ ] npm run test:e2e

## 참고

- ...
```

- 변경사항이 작으면 `참고` 섹션은 생략한다.
- 테스트를 아직 실행하지 않은 상태에서는 검증 항목을 완료 표시하지 않는다.
- 불확실한 내용은 단정하지 말고 "확인 필요"로 표시한다.

3. 개발자에게 초안을 보여주고 승인을 요청한다.
   - 제목과 본문을 그대로 제시한다.
   - "이 초안으로 진행할까요? 수정할 제목이나 본문이 있으면 알려주세요."라고 묻는다.
   - 사용자가 수정안을 주면 반영한 뒤 다시 승인받는다.

4. 승인 후 E2E를 실행한다.
   - `npm run test:e2e`를 실행한다.
   - 실패하면 PR 생성을 중단하고 아래 안내를 출력한다.

```text
E2E가 실패하여 PR 생성을 중단합니다.

다음 순서로 처리하세요.
① Trace Viewer 실행 (npx playwright show-report) → 실패 지점 확인
② 어느 레이어(API/렌더링/로직)에서 깨졌는지 판별
③ 해당 단위 테스트에 케이스 추가 (Red)
④ 프로덕션 코드 수정 (Green) → 다시 /create-pr

⚠ E2E 코드를 고쳐 통과시키는 것은 금지 — 근본 원인 회피.
```

- 실패 로그의 핵심 원인과 관련 파일이 보이면 함께 요약한다.
- `npx playwright show-report`는 사용자가 요청하거나 필요하다고 승인한 경우에만 실행한다.

5. E2E가 통과하면 push와 PR 생성을 진행한다.
   - 원격 브랜치가 없으면 `git push -u origin <current-branch>`를 사용한다.
   - 원격 브랜치가 있으면 `git push`를 사용한다.
   - PR 생성은 우선 사용 가능한 GitHub MCP를 사용하고, MCP가 없거나 부족하면 `gh pr create --base <base> --head <branch> --title "<title>" --body "<body>"`를 사용한다.
   - `gh` 인증, 원격 저장소, 권한 문제로 실패하면 실패 원인과 사용자가 실행할 수 있는 다음 명령을 제시한다.

6. 완료 보고를 한다.
   - PR URL을 포함한다.
   - 실행한 검증 명령과 결과를 요약한다.
   - 생성하지 못했다면 어느 단계에서 멈췄는지와 다음 조치를 짧게 제시한다.

## 프로젝트 특화 참고

- 이 저장소는 Notes App이며 `AGENTS.md`의 Git 워크플로우와 TDD 이슈 사이클을 따른다.
- 커밋 메시지나 PR 제목은 한국어 기반으로 작성한다.
- PR base는 보통 `main`이다. 이슈 의존성이 있는 기능 브랜치라면 선행 이슈가 머지된 `feat` 브랜치를 base로 삼을 수 있다.
- 코드 변경 검증은 요청 범위에 맞춰 좁게 실행하되, PR 생성 직전 검증은 이 스킬의 필수 단계인 `npm run test:e2e`를 우선한다.
