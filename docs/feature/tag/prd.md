# 태그 기능 PRD

## 개요

태그 기능은 사용자가 노트에 짧은 분류명을 붙이고, 같은 태그가 붙은 노트를 모아 확인할 수 있게 하는 기능이다.

현재 Notes App은 사이드바의 노트 목록과 메인 편집 영역을 중심으로 동작한다. 태그 기능은 이 흐름을 크게 바꾸지 않고, 노트 편집 화면 안에서 태그를 추가·삭제하고 별도의 태그 모드에서 태그별 노트 묶음을 확인하는 방향으로 제공한다.

이번 범위의 핵심은 별도 태그 리소스를 만들지 않고 각 `Note`의 `tags: string[]` 값을 기반으로 태그 목록, 태그별 노트 수, 최근 저장일, 자동완성 후보를 파생하는 것이다. 태그는 전역 엔티티가 아니라 노트에 저장된 문자열 값의 집계 결과로 취급한다.

## 목표

- 노트 작성 또는 수정 중 태그를 추가하고 삭제할 수 있다.
- 노트 목록에서 각 노트의 주요 태그를 빠르게 확인할 수 있다.
- 태그 모드에서 전체 태그 목록을 확인하고 검색할 수 있다.
- 특정 태그가 붙은 노트들을 한 화면에서 모아 볼 수 있다.
- 기존 노트 저장 흐름, Context 상태 관리, API 호출 경계를 유지한다.
- 태그 입력값의 정규화, 검증, 중복 판단 기준을 일관되게 적용한다.
- 태그 편집 중 미저장 변경이 의도치 않게 사라지지 않도록 보호한다.

## 사용자 스토리(시나리오)

### 노트에 태그 추가

사용자는 노트 편집 화면에서 제목 아래, 본문 위의 태그 입력 영역에 태그명을 입력한다. `Enter` 또는 추가 버튼으로 태그를 현재 노트의 태그 칩 목록에 추가한다. 입력값이 쉼표로 구분되어 있으면 여러 태그를 한 번에 추가할 수 있다.

사용자가 `React, TypeScript, Vite`를 입력하면 세 개의 태그가 각각 칩으로 추가된다. 일부 입력이 유효하지 않으면 아무 태그도 추가하지 않고 첫 번째 오류를 인라인으로 보여준다.

### 기존 태그 재사용

사용자가 태그를 입력하기 시작하면 이미 저장된 전체 노트의 태그 집계 결과를 기반으로 자동완성 후보가 표시된다. 사용자는 마우스 또는 키보드로 후보를 선택할 수 있으며, 선택하면 즉시 현재 노트의 태그 칩으로 추가된다.

자동완성은 대소문자를 구분하지 않는 prefix 검색으로 동작한다. 현재 노트에 이미 추가된 태그는 후보에서 제외한다.

### 태그 삭제

사용자는 노트 편집 화면의 태그 칩에 있는 삭제 버튼으로 현재 노트에서 태그를 제거한다. 칩 자체를 클릭해도 다른 화면으로 이동하지 않는다.

삭제 버튼은 키보드로 접근 가능해야 하며, 마우스 hover 또는 버튼 focus 시 명확히 드러난다.

### 태그만 변경 후 저장

사용자는 제목이나 본문을 변경하지 않고 태그만 변경해도 저장할 수 있다. 저장이 성공하면 응답 값을 기준으로 Context 상태가 갱신되고, 태그 입력값·오류·자동완성 상태는 초기화된다.

저장에 실패하면 사용자가 입력한 제목, 본문, 태그, dirty 상태는 유지된다.

### 미추가 태그가 남아 있는 상태에서 저장

사용자가 태그 입력창에 텍스트를 입력했지만 아직 추가하지 않은 상태에서 저장 버튼을 누르면 자동으로 태그를 추가하지 않는다. 안내 모달을 표시하고, 사용자가 직접 태그를 추가하거나 입력값을 지운 뒤 다시 저장하도록 한다.

### 미저장 변경 보호

사용자가 태그를 포함한 노트 편집 내용을 변경한 뒤 다른 노트를 선택하거나 새 노트를 만들거나 태그 모드로 진입하려고 하면 미저장 변경 확인 모달을 표시한다.

사용자가 계속 이동을 선택하면 현재 편집 상태를 마지막 저장 상태로 초기화하고 이동한다. 취소를 선택하면 현재 편집 화면에 머문다.

브라우저 새로고침, 탭 닫기, 다른 URL 이동에 대해서는 `beforeunload` 기본 경고를 사용한다.

### 사이드바에서 노트 태그 확인

사용자는 기존 노트 목록에서 각 노트의 태그를 최대 2개까지 확인할 수 있다. 더 많은 태그가 있으면 `+N` 형식으로 남은 개수를 표시한다.

### 태그 목록 확인

사용자는 사이드바 상단의 태그 버튼을 눌러 태그 모드로 진입한다. 태그 모드에서는 기존 사이드바/노트 편집 화면 대신 전체 화면 태그 목록을 본다.

태그 목록은 저장된 노트들의 태그를 집계해 만든다. 각 태그 카드에는 대표 태그명, 포함 노트 수, 최근 저장일을 표시한다.

### 태그 검색

사용자는 태그 목록 화면의 검색 입력으로 태그를 prefix 방식으로 검색한다. 검색은 대표 표시명을 기준으로 하며 대소문자를 구분하지 않는다.

검색 결과가 없으면 태그 목록 영역에 검색 결과 없음 문구만 표시한다. 검색어가 있을 때만 입력창 안의 지우기 버튼을 표시한다.

### 태그별 노트 모아보기

사용자는 태그 카드 전체를 클릭해 태그 상세 화면으로 이동한다. 태그 상세 화면에서는 해당 태그가 붙은 노트 수와 노트 카드 목록을 확인한다.

노트 카드를 클릭하면 태그 모드를 종료하고 해당 노트를 선택한 일반 노트 편집 화면으로 이동한다.

### 태그 모드에서 노트로 돌아가기

사용자는 태그 목록 또는 태그 상세 화면에서 노트로 돌아가기 버튼을 눌러 일반 노트 모드로 돌아간다. 태그 모드 진입 직전에 선택했던 노트가 아직 존재하면 그 노트가 다시 선택된다. 해당 노트가 삭제되어 없으면 선택 없음 상태로 돌아간다.

## 기능 요구사항

### 데이터 모델

- `Note` 타입은 `tags: string[]`를 포함한다.
- 별도의 `tags` JSON Server 리소스는 만들지 않는다.
- API 응답에 `tags`가 없으면 클라이언트에서 `[]`로 보정한다.
- 노트 생성·수정 요청에는 항상 `tags: string[]`를 포함한다.
- 기존 `db.json`의 노트에는 `tags: []`를 추가한다.

### 태그 정규화와 비교

- 저장 전 태그 입력값은 앞뒤 공백을 제거하고 내부 연속 공백을 한 칸으로 축약한다.
- 입력한 대소문자는 보존한다.
- `#`는 제거하지 않고 일반 문자로 취급한다.
- 중복 판단, 검색, 집계에는 비교 키를 사용한다.
- 비교 키는 정규화된 값을 소문자로 변환한 값이다.
- `#React`와 `React`는 서로 다른 태그로 취급한다.
- `React Query`, `React  Query`, `react query`는 같은 비교 키를 가진 태그로 취급한다.

### 태그 검증

- 정규화된 태그는 최소 2자 이상, 최대 20자 이하여야 한다.
- 허용 문자는 완성형 한글 음절, ASCII 영문자, ASCII 숫자, 공백, `-`, `_`, `#`이다.
- `#` 한 글자는 허용하지 않고, `##`는 허용한다.
- `--`, `__`, `##`, `# #`처럼 기호만 있는 태그도 길이와 허용 문자 조건을 만족하면 허용한다.
- 공백만 있는 입력과 쉼표 분리 결과의 빈 조각은 오류 없이 무시한다.
- 기존 저장 데이터에 유효하지 않은 태그가 있으면 집계에서는 제외하고, 편집 화면에서는 경고 스타일의 칩으로 보여준다.

### 태그 추가와 중복 처리

- `Enter` 또는 추가 버튼으로 태그를 추가한다.
- 쉼표가 포함된 입력은 추가 시점에만 분리한다.
- 입력 중 쉼표만으로 자동 칩을 만들지 않는다.
- 태그 추가 성공 후 입력창 focus를 유지한다.
- 현재 노트에 이미 있는 태그를 다시 입력하면 중복 추가하지 않고 오류 메시지도 표시하지 않는다.
- 한 번에 여러 태그를 추가할 때 입력 묶음 안의 중복 태그는 하나로 합친다.
- 노트 하나에는 최대 5개의 태그를 추가할 수 있다.
- 최대 개수 검사는 현재 노트에 실제로 새로 추가되는 태그 수를 기준으로 한다.

### 자동완성

- 자동완성 후보는 저장된 전체 노트의 태그 집계 결과에서 만든다.
- 현재 노트에 이미 있는 태그는 후보에서 제외한다.
- 대소문자를 구분하지 않는 prefix 검색으로 매칭한다.
- 초성 검색은 지원하지 않는다.
- 최대 3개 후보만 표시한다.
- 후보는 더 짧게 일치하는 태그, 사용 빈도가 높은 태그, 최근 사용된 태그 순으로 우선한다.
- 후보를 선택하면 즉시 현재 노트의 태그 칩으로 추가한다.

### 태그 집계와 대표 표시명

- 태그 집계 결과는 비교 키, 대표 표시명, 포함 노트 수, 최근 저장일을 포함한다.
- 같은 노트 안에 같은 비교 키의 태그가 중복되어 있으면 포함 노트 수는 하나로 계산한다.
- 대표 표시명은 같은 비교 키를 가진 태그 중 가장 많이 사용된 표기를 사용한다.
- 사용 횟수가 같으면 가장 최근에 저장된 표기를 대표 표시명으로 사용한다.
- 대표 표시명의 공백은 정규화된 한 칸 공백을 사용한다.
- 최근 저장일은 해당 태그가 붙은 노트 중 가장 최신 `updatedAt` 값이다.

### 태그 모드

- `App`은 일반 노트 모드와 태그 모드를 상태로 관리한다.
- 태그 모드는 URL 라우팅을 새로 만들지 않고 앱 내부 상태로만 전환한다.
- 태그 모드에 진입할 때 기존 선택 노트 ID를 기억한다.
- 태그 모드를 종료하면 기억한 노트가 존재하는 경우 다시 선택한다.
- 태그 모드 재진입 시 이전 검색어 또는 이전 상세 화면 상태를 복원하지 않고 태그 목록 초기 상태로 시작한다.

### 태그 목록 화면

- 태그 목록 화면은 화면 제목, 노트로 돌아가기 버튼, 검색 입력, 태그 카드 그리드를 포함한다.
- 태그가 없으면 빈 상태 문구와 노트로 돌아가기 버튼을 표시한다.
- 검색 결과가 없으면 검색 결과 없음 문구만 표시한다.
- 검색어가 없을 때는 최근 저장일 내림차순으로 정렬한다.
- 검색어가 있을 때는 더 짧게 일치하는 태그, 최근 저장일 내림차순, 대표 표시명 가나다/알파벳순으로 정렬한다.

### 태그 상세 화면

- 태그 상세 화면은 대표 태그명, 태그 목록으로 돌아가기 버튼, 노트로 돌아가기 버튼, 포함 노트 수, 노트 카드 목록을 포함한다.
- 태그 상세의 노트 목록은 `updatedAt` 내림차순으로 정렬한다.
- 노트 카드는 제목, 본문 미리보기, 최근 저장일, 전체 태그 칩을 표시한다.
- 제목이 비어 있으면 `(제목 없음)`으로 표시한다.
- 본문이 비어 있으면 본문 미리보기 영역은 숨긴다.
- 상세 화면을 보는 동안 해당 태그가 모든 노트에서 사라지면 태그 목록 화면으로 이동하고 안내 메시지를 표시한다.

### 로딩과 오류

- 태그 데이터는 노트 상태에서 파생되므로 기존 노트 로딩 상태를 공유한다.
- 기존 `error` 상태가 있으면 태그 모드에서도 오류를 표시한다.
- 오류가 있어도 보유한 `notes` 상태가 있으면 태그 UI는 계속 렌더링할 수 있다.

## 수용 기준

- 사용자는 노트 편집 화면에서 태그를 추가·삭제하고 저장할 수 있다.
- 태그만 변경해도 저장 버튼이 활성화되고 저장 후 `updatedAt`이 갱신된다.
- 유효하지 않은 태그 입력은 저장되지 않고 인라인 오류로 안내된다.
- 노트 하나에 태그는 최대 5개까지만 추가된다.
- 자동완성은 저장된 태그를 기반으로 최대 3개까지 표시된다.
- 태그 목록 화면은 전체 노트에서 파생한 태그 카드 목록을 표시한다.
- 태그 상세 화면은 선택한 태그가 붙은 노트만 표시한다.
- 미저장 변경이 있는 상태에서 화면 전환 또는 브라우저 이탈 시 변경 손실을 방지한다.
- 컴포넌트는 직접 `fetch`를 호출하지 않고 기존 API 모듈 또는 Context 액션을 통해 데이터에 접근한다.

## 기술 선택

태그 기능은 커스텀 훅 기반 합성 방식으로 구현한다.

### Context

현재 앱은 React 순수 API 중심의 단순한 구조를 가진다. `NotesContext`는 노트 서버 상태와 CRUD 액션을 소유하고, `App`은 선택 노트와 생성 상태를 관리하며, `NoteEditor`는 제목/본문 편집 로컬 상태를 관리한다.

태그 기능은 단순 필드 추가보다 복잡하다. 태그 정규화, 검증, 쉼표 일괄 추가, 중복 제거, 자동완성, dirty 판정, 미저장 변경 보호, 태그 목록/상세 파생 데이터가 필요하다. 이 로직을 `NoteEditor`나 `NotesContext`에 직접 누적하면 컴포넌트와 Context 책임이 과도하게 커질 수 있다.

이번 명세는 태그를 별도 리소스가 아닌 `Note.tags: string[]`로 저장하도록 확정한다. 따라서 서버 상태 관리 구조는 기존 노트 CRUD 패턴을 유지하고, 태그 관련 복잡도는 클라이언트의 순수 함수와 커스텀 훅으로 분리하는 것이 적합하다.

### Decision

태그 기능은 다음 구조로 구현한다.

- `src/utils/tags.ts`에 태그 정규화, 비교 키 생성, 검증, 일괄 추가, 집계, 검색, 정렬, 자동완성 후보 계산 같은 순수 로직을 둔다.
- `src/types/tag.ts`에 태그 집계와 태그 화면에서 사용하는 파생 타입을 둔다.
- `useNoteEditorState` 같은 커스텀 훅을 만들어 제목, 본문, 태그 목록, 태그 입력값, 태그 오류, 자동완성 상태, dirty 판정을 합성한다.
- `NotesContext`는 기존처럼 노트 서버 상태와 `createNote`, `updateNote`, `deleteNote`를 제공하는 역할에 집중한다.
- `App`은 `notes`/`tags` 모드, 선택 노트, 생성 상태, 태그 모드 내비게이션, 미저장 변경 보호 흐름을 관리한다.
- `NoteEditor`는 편집 화면 조립과 저장 트리거를 담당하고, 세부 태그 UI는 `TagInput`, `TagChip`, `TagAutocomplete` 같은 작은 컴포넌트로 분리한다.
- 태그 목록과 상세 화면은 저장된 `notes` 상태에서 파생한 데이터를 사용하며, 별도 서버 리소스나 전역 태그 상태를 만들지 않는다.

이 방식은 React의 `useState`, `useEffect`, `useMemo`, 커스텀 훅, Context 같은 순수 API를 적극 활용한다. 이후 구현에서도 화면 컴포넌트에 복잡한 상태 전이를 직접 쌓기보다, 커스텀 훅과 순수 유틸을 조합하는 방향을 기본 원칙으로 삼는다.

### Alternatives

검토한 대안은 다음과 같다.

| 대안                     | 장점                                                                                                                                                                 | 단점                                                                                                                                                     | 판단                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 최소 확장 방식           | 초기 구현이 빠르고 기존 컴포넌트 구조 변경이 작다.                                                                                                                   | `NoteEditor`에 태그 입력, 검증, 자동완성, dirty, 모달 트리거가 누적되어 컴포넌트가 비대해진다. UI 테스트도 많은 상태 조합을 한 컴포넌트에서 다뤄야 한다. | 단기 구현에는 유리하지만 이번 명세의 복잡도에는 부적합하다.      |
| 커스텀 훅 기반 합성 방식 | 태그 순수 로직, 편집 상태 전이, 화면 컴포넌트를 분리할 수 있다. React 순수 API를 활용하면서 기존 Context/API 경계를 유지한다. 단위 테스트와 UI 테스트를 나누기 쉽다. | hook과 컴포넌트 파일 수가 늘어나며, hook의 입출력 계약을 명확히 관리해야 한다. 태그 변경은 저장 전까지 로컬 상태에만 존재한다.                           | 채택한다. 현재 명세와 가장 잘 맞고 이후 확장 기준으로 삼기 좋다. |
| Context 확장 방식        | 여러 컴포넌트에서 태그 집계와 태그 액션에 접근하기 쉽다.                                                                                                             | `NotesContext`가 서버 상태, 파생 데이터, UI 편집 액션까지 소유하게 되어 책임이 흐려진다. Context 변경 시 렌더링 영향 범위도 넓어진다.                    | 기존 CRUD 중심 Context 패턴을 유지하기 위해 채택하지 않는다.     |
| 태그 전용 리소스 방식    | 전역 태그 수정, 삭제, 메타데이터 확장에는 유리하다.                                                                                                                  | 별도 `tags` API 리소스를 만들지 않는다는 명세와 충돌한다. 노트의 `tags` 배열과 전역 태그 리소스 간 동기화 문제가 생긴다.                                 | 이번 범위에서 명시적으로 제외한다.                               |
| 태그 즉시 저장 방식      | 태그 칩 추가/삭제 시 서버 상태가 바로 확정되어 별도 저장 버튼을 기다리지 않는다.                                                                                     | 현재 명세의 저장 버튼 중심 편집 흐름, 미저장 변경 보호, 저장 실패 시 입력 유지 정책과 맞지 않는다. 태그만 별도 저장되는 예외 흐름이 생긴다.              | 이번 범위에서는 채택하지 않는다.                                 |

### Consequences

선택한 방식의 결과와 트레이드오프는 다음과 같다.

장점:

- 태그 도메인 로직이 순수 함수로 분리되어 단위 테스트가 쉽다.
- 편집 상태 전이가 커스텀 훅에 모이므로 `NoteEditor` UI 테스트와 hook 테스트를 분리할 수 있다.
- `NotesContext`의 기존 CRUD 패턴을 유지하므로 API 경계와 상태 갱신 규칙이 흔들리지 않는다.
- 태그 목록과 상세 화면은 저장된 `notes`에서 파생되므로 별도 동기화 문제가 줄어든다.
- 저장 실패 시 편집 상태를 유지하기 쉽고, dirty 판정과 미저장 변경 보호를 일관되게 구현할 수 있다.
- 향후 유사하게 복잡한 편집 기능도 커스텀 훅 기반 합성 방식으로 확장하는 기준이 생긴다.

단점:

- 컴포넌트 파일과 hook 파일이 늘어난다.
- `useNoteEditorState` 같은 hook의 입력과 반환값 계약을 명확히 관리해야 한다.
- 태그 추가/삭제는 즉시 서버에 저장되지 않고 로컬 편집 상태에 반영된다.
- 사용자는 저장 버튼을 눌러야 태그 변경을 확정할 수 있다.
- hook이 너무 많은 책임을 갖지 않도록 태그 순수 로직은 반드시 `src/utils/tags.ts`에 남겨야 한다.

## Out of Scope(현재 상황에서 개발하면 안되는 것)

- 별도의 `tags` API 리소스 또는 JSON Server 컬렉션을 만들지 않는다.
- 태그를 노트와 독립된 전역 엔티티로 관리하지 않는다.
- 전역 태그 이름 변경 기능을 만들지 않는다.
- 전역 태그 삭제 기능을 만들지 않는다.
- 태그 관리 전용 CRUD 화면을 만들지 않는다.
- 태그 색상, 아이콘, 설명, 즐겨찾기 같은 메타데이터를 만들지 않는다.
- 태그별 권한, 공유, 협업 기능을 만들지 않는다.
- 태그 병합, 분리, 일괄 치환 기능을 만들지 않는다.
- 태그 상세 안에서 노트를 다시 검색하는 기능을 만들지 않는다.
- 한글 초성 검색을 지원하지 않는다.
- fuzzy search, contains search, 정규식 검색을 지원하지 않는다.
- `/tags`, `/tags/:tag` 같은 URL 경로를 만들지 않는다.
- 브라우저 히스토리 기반의 태그 모드 뒤로가기/앞으로가기를 만들지 않는다.
- 태그 모드의 검색어, 선택 태그, 상세 화면 상태를 앱 재진입 또는 모드 재진입 시 복원하지 않는다.
- 태그 칩 클릭만으로 태그 모드나 태그 상세로 이동하지 않는다.
- 빈 태그 입력창에서 `Backspace`로 마지막 태그를 삭제하는 동작을 만들지 않는다.
- 검색 결과 없음 상태에서 별도의 검색어 지우기 버튼을 목록 영역에 추가하지 않는다.
- 태그 입력값을 저장 시 자동으로 칩으로 변환하지 않는다.
- 미추가 태그 안내 모달에서 확인 외의 추가 액션을 만들지 않는다.
- 서버 사이드 집계, 서버 사이드 검색, 서버 사이드 정렬을 만들지 않는다.
- 태그 집계 결과를 별도 캐시나 영구 저장소에 저장하지 않는다.
- 대규모 데이터셋을 위한 가상 스크롤, 페이지네이션, 무한 스크롤을 만들지 않는다.
- 모바일 전용 제스처, 드래그 앤 드롭, 태그 순서 재배치 기능을 만들지 않는다.
- 노트 목록의 기존 정렬 기준을 태그 기능 때문에 변경하지 않는다.
- 제목/본문의 기존 검증 정책을 태그 기능 범위에서 바꾸지 않는다.
- 기존 문자열을 태그 기능과 무관하게 대규모로 수정하지 않는다.
- 디자인 시스템 문서 범위를 넘어 UI 전반의 색상, 간격, 타이포그래피를 재설계하지 않는다.

## 용어 정의

- 태그: 노트에 붙이는 짧은 분류 문자열. 이번 범위에서는 `Note.tags` 배열의 문자열 값이다.
- 태그 칩: 노트 편집 화면이나 카드에서 태그를 시각적으로 표시하는 작은 UI 요소.
- 대표 표시명: 같은 비교 키를 가진 여러 태그 표기 중 목록과 상세 화면에 대표로 보여줄 태그명.
- 비교 키: 중복 판단, 검색, 집계에 사용하는 내부 문자열. 정규화된 태그를 소문자로 변환한 값이다.
- 정규화: 태그 입력값의 앞뒤 공백을 제거하고 내부 연속 공백을 한 칸으로 축약하는 처리.
- 태그 집계: 저장된 노트들의 `tags` 값을 모아 태그별 노트 수, 대표 표시명, 최근 저장일을 계산하는 처리.
- 태그 모드: 일반 노트 편집 화면 대신 태그 목록 또는 태그 상세를 보여주는 앱 내부 화면 상태.
- 태그 목록 화면: 전체 태그를 검색하고 카드로 확인하는 태그 모드의 기본 화면.
- 태그 상세 화면: 특정 태그가 붙은 노트를 모아 보여주는 화면.
- 미추가 태그: 태그 입력창에는 남아 있지만 아직 현재 노트의 태그 칩 목록에 추가되지 않은 텍스트.
- dirty 상태: 마지막 저장 상태와 현재 편집 상태가 달라 저장하지 않은 변경이 있는 상태.
- Out of Scope: 이번 태그 기능 구현 범위에서 의도적으로 만들지 않는 기능 또는 변경.
